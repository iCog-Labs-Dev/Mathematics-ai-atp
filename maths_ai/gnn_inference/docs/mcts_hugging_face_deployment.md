# Publish and fetch MCTS serving artifacts

For deployment users who only need to download and serve a published release,
see the [generic Docker host guide](../../../docker/HUGGING_FACE_DEPLOYMENT.md).
The local `upload-receipt.json` described below is specific to publishing;
deployment users can obtain the release commit and manifest digest from the
publisher without receiving that receipt.

The upload command publishes a selected RL checkpoint and its matching serving artifacts to a **new branch** in `iCogLabs-Dev/Mathlib-Sexpr-GNN`. The default release is `v2.0.1`. It preserves `main`, earlier versions, and unrelated inherited files. It does not create a tag with the same name.

The download command verifies every file and the model/retrieval bindings, then exposes a persistent deployment directory for the existing Docker mounts. Neither API startup nor the Docker image build automatically downloads this release.

## Before uploading

- Pull the application changes containing these commands into JupyterHub. Use the project's installed environment, including its pinned custom Pantograph client.
- Wait until the selected run has finished writing its checkpoint. Choose `best.pt` for the checkpoint selected by periodic evaluation, or `last.pt` for the final saved model. They need not contain the same weights, and `best.pt` may not exist if evaluation never ran.
- Preserve the original deployment artifacts referenced by the run's saved `config.json`. Publishing validates their pairing and the actual JupyterHub Lean environment. It does not repair a stale deployment.
- Review repository visibility, distribution licenses, Hugging Face storage quota, and write permissions. Uploads use the repository's existing visibility. The corpus and prepared metadata may have different redistribution terms from your code.
- The selected checkpoint is uploaded **unchanged**. RL checkpoint files can contain optimizer states, replay samples, PLN runtime information, and other training metadata, including embedded paths. The local plan prints the extra top-level checkpoint fields. Inspect the checkpoint before sharing if that information is sensitive. This command does not strip fields or create a weights-only checkpoint.
- Configurations generated by the tool use container paths. The raw run configuration, local source-path receipt, logs, and credentials are not uploaded. Source paths remain in the local receipt directory; keep that directory private.
- Hashing reads the index and corpus several times. Uploading does not stage another full copy of those files, but network transfer and hashing can take time. Downloading requires persistent free space for the complete serving bundle and possible partial-transfer overhead. Free-space checks cannot establish your filesystem quota.
- Treat the checkpoint publisher as trusted. Existing model loaders use PyTorch pickle loading; a checksum detects changed content but does not make an untrusted checkpoint safe to execute.

## 1. Activate Python and log in

From a JupyterLab terminal:

```bash
conda activate atp-mcts
cd /home/jovyan/Nol/Mathematics-ai-atp

python - <<'PY'
from huggingface_hub import login
login()
PY
```

Enter a token with write access to `iCogLabs-Dev/Mathlib-Sexpr-GNN`. Do not paste it into a script or a committed JSON file. Existing Hugging Face login or an externally supplied `HF_TOKEN` also works. A public release can be downloaded without that write token; use a read token when private access is required.

## 2. Select the run and generate a local plan

Replace the timestamp below with the actual completed run directory printed by RL. All artifact roots are read from its `config.json`, so no copying into a new source layout is required.

```bash
export RUN="/home/jovyan/Nol/Mathematics-ai-atp/runs/rl_puct_no_pln_full/REPLACE_WITH_RUN_TIMESTAMP"
export CHECKPOINT="$RUN/last.pt"
export RECEIPT="$HOME/mcts-release-receipts/v2.0.1"

python -m maths_ai.gnn_inference.scripts.publish_mcts_deployment \
  --run-dir "$RUN" \
  --checkpoint "$CHECKPOINT" \
  --receipt-dir "$RECEIPT" \
  --version v2.0.1 \
  --device cpu
```

For a PLN best-first run, change `RUN` to its timestamped directory. To publish the selected best checkpoint, set `CHECKPOINT="$RUN/best.pt"`.

The default serving device is CPU. To generate a GPU serving configuration, use `--device cuda:0` in **both** planning and upload commands and later start the GPU Compose service. The trained weights can be served on either device; the generated configuration must match the deployment hardware.

This command validates the selected checkpoint, exact prepared vocabularies/graph metadata, retrieval files, corpus, inventory, and source Lean identity. It creates only small generated files and private receipts locally. Without `--upload`, it performs no remote writes. It does not require activating the PLN shell runtime merely to package a run that used PLN; PeTTa is not executed during packaging.

Review the file list, sizes, generated `config/` files under `$RECEIPT/generated`, and retained checkpoint fields. The minimal prepared root contains only:

```text
prepared/vocab/node_vocab.json
prepared/vocab/tactic_vocab.json
prepared/metadata/graph_representation.json
```

Prepared graph shards and retrieval training caches are excluded. The complete exported query artifact, six index files including its deployment manifest, corpus, and declaration inventory are included.

## 3. Publish v2.0.1

Run the same command with `--upload`:

```bash
python -m maths_ai.gnn_inference.scripts.publish_mcts_deployment \
  --run-dir "$RUN" \
  --checkpoint "$CHECKPOINT" \
  --receipt-dir "$RECEIPT" \
  --version v2.0.1 \
  --device cpu \
  --upload
```

The tool creates `v2.0.1` from the resolved `main` commit and adds the release in one parent-commit-protected commit. It refuses an existing version unless the same local receipt proves a retry of this operation. Retry an interrupted upload using the identical command and receipt directory. If source files, generated configuration, application provenance, or manifest contents change, use a fresh receipt and a new release name when the previous version has already been published. Never remove the receipt to force an existing release overwrite.

The resulting branch contains:

```text
deployments/mcts/v2.0.1/
├── release.json
├── README.md
├── artifacts/
│   ├── checkpoint.pt
│   ├── prepared/
│   ├── query/
│   ├── index/
│   ├── lemmas.jsonl
│   └── declarations.json
└── config/
    ├── rl.json
    └── service.json
```

The generated service config exposes PUCT, best-first, and their PLN-enabled profiles. The default matches the training run's search mode and PLN setting. It supplies a pinned Hugging Face dataset evaluation profile. Custom JSONL datasets are not uploaded implicitly; add and configure those separately when needed for dataset evaluation. Single-goal proving does not require a dataset file in this release.

`$RECEIPT/upload-receipt.json` records the full release commit and manifest digest. Remote verification checks manifest bytes, the exact release file list, and file sizes. It does not claim to have downloaded and rehashed every large remote file. The fetch command performs that full verification.

## 4. Download to persistent storage

Extract the immutable deployment identifiers from the receipt:

```bash
export HF_RELEASE_COMMIT="$(python - <<'PY'
import json, os
from pathlib import Path
print(json.loads((Path(os.environ['RECEIPT']) / 'upload-receipt.json').read_text())['commit'])
PY
)"
export HF_RELEASE_MANIFEST="$(python - <<'PY'
import json, os
from pathlib import Path
print(json.loads((Path(os.environ['RECEIPT']) / 'upload-receipt.json').read_text())['manifest_sha256'])
PY
)"

python -m maths_ai.gnn_inference.scripts.fetch_mcts_deployment \
  --revision "$HF_RELEASE_COMMIT" \
  --manifest-sha256 "$HF_RELEASE_MANIFEST" \
  --version v2.0.1 \
  --output /home/jovyan/mcts-deployments/v2.0.1
```

Use persistent storage, not `/tmp`. Downloading on the same JupyterHub host still needs space for the downloaded copy. On a different deployment host, transfer the small upload receipt or securely provide its commit and manifest digest, then run the same fetch command there. You do not need the source training run on the download host.

If interrupted, the error identifies the retained backing directory. Rerun with the identical arguments plus `--resume /absolute/path/to/.v2.0.1.bundle-...`. Verified completed files are reused. A corrupt existing file is rejected rather than silently accepted. After success the output is a relative symlink to its hidden sibling backing directory; **retain that sibling directory**. Do not move or delete it independently.

The default maximum declared serving size is 100 GiB. Set `--max-bytes` explicitly if a valid release exceeds that bound. Existing unrelated output paths are never replaced.

## 5. Start Docker using the downloaded artifacts

Run from the application repository on a host with Docker access:

```bash
MATHS_AI_ARTIFACTS=/home/jovyan/mcts-deployments/v2.0.1/artifacts \
MATHS_AI_CONFIG=/home/jovyan/mcts-deployments/v2.0.1/config \
docker compose up --build mcts-api
```

For a release generated with `--device cuda:0`, use the GPU service on a host with the NVIDIA container runtime:

```bash
MATHS_AI_ARTIFACTS=/home/jovyan/mcts-deployments/v2.0.1/artifacts \
MATHS_AI_CONFIG=/home/jovyan/mcts-deployments/v2.0.1/config \
docker compose --profile gpu up --build mcts-api-gpu
```

The Docker daemon must see these host filesystem paths. A Docker daemon outside the JupyterHub container may see different paths. Check the existing mounting guidance before using these paths in that arrangement.

### Let a container perform the download

Build the image containing these scripts, create a writable persistent parent, then run a one-shot initialization container:

```bash
docker build -f docker/Dockerfile -t maths-ai-mcts-api .
mkdir -p /home/jovyan/mcts-deployments

docker run --rm \
  --user "$(id -u):$(id -g)" \
  --entrypoint /opt/venv/bin/python \
  -v /home/jovyan/mcts-deployments:/downloads \
  maths-ai-mcts-api \
  -m maths_ai.gnn_inference.scripts.fetch_mcts_deployment \
  --revision "$HF_RELEASE_COMMIT" \
  --manifest-sha256 "$HF_RELEASE_MANIFEST" \
  --version v2.0.1 \
  --output /downloads/v2.0.1
```

The container's `/downloads/v2.0.1` appears at `/home/jovyan/mcts-deployments/v2.0.1` on the host. A failed download prints a container path for `--resume`; rerun the same initialization container with that path. After it succeeds, start Compose with the host mounts above. The API entrypoint is deliberately bypassed for initialization because no model config is mounted yet.

For private releases, supply an externally set read token with `-e HF_TOKEN` to this initialization container. Do not put it in the Dockerfile or image. Public releases do not require passing a token. The API does not need the upload token to serve files already downloaded.

## Runtime compatibility and verification

The download verifies model/retrieval consistency without executing Lean. The API must then verify the actual serving Lean environment before becoming ready:

```bash
curl --fail http://localhost:8000/ready
docker compose logs --tail=100 mcts-api
```

The inventory identity includes **REPL executable bytes and compiled Mathlib contents**, not only source revisions. An independently built Docker image can differ from the JupyterHub runtime even at the same source commit. A successful upload/download therefore does not guarantee readiness.

If environment verification fails, use the existing verified environment-migration workflow against the intended deployment runtime, then publish a new matched release. Alternatively deploy the existing matching runtime, including its toolchain and compiled dependencies. An explicit Compose override can bind the JupyterHub REPL file at `/opt/pantograph/repl` and the compatible Mathlib directory at `/opt/mathlib4`, both read-only, but its executable's system dependencies and toolchain must also work inside the image. Do not replace environment hashes manually or disable the check.

The image supplies Python, the pinned custom client, Lean, SWI-Prolog/Janus, PeTTa, and the chainer fork. The model repository supplies weights and data artifacts. PLN readiness also depends on the image's provisioned runtime; uploading a model does not install or activate PeTTa on JupyterHub.

After readiness succeeds, try a small proof before scheduling dataset evaluations:

```bash
curl --fail http://localhost:8000/prove \
  -H 'Content-Type: application/json' \
  -d '{"goal":"True","hypotheses":[],"search_profile":"best_first_pln","proposal_mode":"sample","seed":42,"timeout_s":60}'
```

This exercises the PLN-enabled profile, but a learned policy is not guaranteed to solve even this control within the budget. Inspect the response and logs for certification and PLN outcomes. Uploading and downloading files is not evidence of proof-search quality.

## Validation boundaries

Offline tests use a fake Hub and tiny real model/tokenizer/FAISS fixtures. They cover release selection, source mutation, checksum failures, retry behavior, safe paths, runtime mismatches, generated configs, and no-overwrite publication. They do not perform a real upload, a full-size download, or an image build against your JupyterHub artifacts.

Hub APIs used here are described in the [upload guide](https://huggingface.co/docs/huggingface_hub/guides/upload), [commit API reference](https://huggingface.co/docs/huggingface_hub/package_reference/hf_api), and [pinned download guide](https://huggingface.co/docs/huggingface_hub/guides/download).
